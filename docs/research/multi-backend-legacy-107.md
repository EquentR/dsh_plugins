# 旧版 dsh 的「非本地访问要求账号密码」改造逆向 + 新版兼容性实测

> 目标主机：`192.168.55.107`（Ubuntu 22.04，主机名 `RAOLEJIA1`）
> 调研日期：2026-10-19
> 调研性质：全程只读侦察 + 隔离环境旁路实测；**未修改现役服务、未停现役进程、未原地升级**
> 结论适用范围：旧版 `@deepseek-ai/dsh@0.1.5-rc.2` → 新版 `0.2.0-rc.2`（npm latest）/ `0.2.1-rc.2`（桌面内置）

---

## 一、结论摘要

- **这套改造不是改核心、不是 nginx、不是 HTTP Basic 裸奔**，而是一个独立 dsh 插件 `@yiln-dsh/dsh-plugin-auth-webserver@0.7.6`：它在 Node 事件循环内对每个**非 loopback NIC 地址**各起一个 HTTP listener，先做「账号密码 / HMAC cookie / TOTP / Passkey」鉴权，再把通过鉴权的请求（含 WebSocket upgrade）反向代理到 core 的 `127.0.0.1:3080`。
- **「非本地」不是靠 `remote_addr` 判断的，而是靠 listener 分离**：core 的 loopback listener 原封不动保留（仍是 token 认证），只有网关 listener 才要求账号密码。因此本机浏览器访问 `127.0.0.1:3080` 走的仍是原生的 token 流程。
- **它与新版 token/cookie 模型是「并行叠加」，不是「替换」**：插件通过 `ctx.connection.authenticatedUrl()` 拿到带 `?token=` 的 URL，自己扮演"合法本地浏览器"完成 303 → `dsh-auth-*` cookie 兑换，把该 cookie 仅存内存；对外则剥掉浏览器带来的所有 `dsh-auth-*` cookie、也不把 core 的 `Set-Cookie` 透传出去。于是形成**双层会话**：远程用户 → 网关账号密码 → 网关 HMAC cookie → 网关持有的 core cookie → core 的 API/WS 鉴权。
- **移植到新版只需 2 处一行级修补即可跑通**（本报告已实测验证）：`settings.register` 变成了可选（新 settings seam 不再有该方法）、core 的 token 兑换 303 的 `Location` 从 `/` 变成了 `./`。除此之外 `webServer.tapIndex`、`clientModules.clientPath/rebuilt`、`connection.authenticatedUrl` 三个关键接缝在 `0.2.0-rc.2` 上全部存活，网关完整链路（登录页 → 登录 → GUI → 421 Host 栅栏 → WebSocket）实测全通。
- **是否值得借鉴取决于目标**：新版 `0.2.1-rc.2`（桌面内置）已原生支持绑具体局域网 IP + TLS + `--public-url`，**不需要**网关也能远程访问；但新版鉴权仍是「单一进程 token → 单一 cookie → 所有通过认证者都是 owner」，**没有多用户、没有账号密码、没有 logout**。所以这套改造的可借鉴点在于「**多用户/可撤销的账号体系 + 显式登出 + 审计（client 列表）**」，而不在于「能不能远程访问」。

## 三、鉴权改造逆向（核心）

### 3.1 总体架构：进程内认证网关反向代理

```
                        ┌─────────────────────────────── 同一个 node 进程 (pid 2942221) ───────────────────────────────┐
                        │                                                                                            │
远程浏览器 ──HTTP──▶  [ listener 192.168.55.107:3080 ]                                                            │
  (LAN/公网)            │  1. validateGatewayRequest()  Host/Origin 栅栏  → 421 / 403                              │
                        │  2. checkAuth()  cookie(HMAC) / Basic                                                      │
                        │     失败 → sendUnauthorized() → 登录页(200 HTML) 或 401 JSON                              │
                        │  3. proxyRequest() ──▶ http://127.0.0.1:3080                                             │
                        │        · 剥掉浏览器携带的所有 dsh-auth-* cookie                                            │
                        │        · 换成网关独占的 core cookie（内存里的）                                             │
                        │        · 剥掉 ?token=                                                                     │
                        │     同时 proxyUpgrade() 对 WebSocket 做同样的事                                            │
                        │                                                                                            │
本机浏览器 ──HTTP──▶  [ listener 127.0.0.1:3080 ] ── core 原生 web server（token → cookie），行为完全不变            │
                        │                                                                                            │
                        └────────────────────────────────────────────────────────────────────────────────────────────┘
```

关键点：**它是"新增一个模块"，不是"替换原模块"**。插件 README 原话：

> "So the default web module is a *new* module instead of a replacement: local access behaves exactly like stock DSH, and LAN clients get the full GUI behind authentication."

### 3.2 「非本地访问」如何判定 —— listener 分离，而非 `remote_addr`

这是最容易被误解的一点。**代码里没有任何"根据 remote_addr 判断是否本地、再决定要不要密码"的分支**。

真正机制是：

1. 插件的 `pickAddresses(config)`（`index.js:413`）返回**所有非 internal 的 IPv4 地址**；部署时被 `cordis.patch.yml` 显式收敛成只有一个（见 §3.7）。
2. `apply()` 末尾对每个地址执行 `server.listen(config.port, record.address)`（`index.js:2022`）——**逐 IP 绑定，绝不用 `0.0.0.0`**。源码注释解释了原因：`0.0.0.0` 会和 core 的 loopback listener 端口冲突。
3. 因此"是不是本地访问"由**客户端连的是哪个 socket 地址**隐式决定：
   - 连 `127.0.0.1:3080` → 打到 core，走 token 流程，**不需要账号密码**
   - 连 `192.168.55.107:3080` → 打到网关，**必须先登录**

`remote_addr` 只用于两件次要的事：会话记录里的 `address` 字段，以及限流 key；并且在存在可信代理时才用 `X-Forwarded-For` 取真实客户端（`clientAddress()`，`index.js:653`）。

### 3.3 鉴权机制：自研登录页 + HMAC cookie（不是 HTTP Basic）

**是三者都用了，但主力是"自研登录页 + HMAC 签名 cookie"**：

| 机制 | 是否支持 | 位置 | 说明 |
|---|---|---|---|
| 自研表单登录页 | ✅ **主力** | `login-page.js`（300 行） | 中英双语，`<form id="login" method="post" action="/api/auth.login?lang=xx">`，JS `fetch` 提交 JSON |
| HMAC 签名 cookie | ✅ **主力** | `index.js:1072-1109` | `dsh_auth_token` = `sessionId.issuedAt.HMAC-SHA256(...)`，HttpOnly + SameSite=Strict |
| HTTP Basic | ✅ 兼容 | `index.js:194` `parseBasic()` | 便于 `curl -u` 与自动化；**一旦启用 TOTP 就被完全禁用**（Basic 无法承载第二因子） |
| TOTP 2FA | ✅ 可选 | `totp.js`（78 行） | RFC 6238，SHA-1/6 位/30 秒，±1 窗口，且做了**同一验证码 90 秒内不可重放** |
| WebAuthn Passkey | ✅ 可选 | `passkey-store.js`、`index.js:1381+` | `@simplewebauthn/server@13.3.3`；需 HTTPS（localhost 例外） |
| 反向代理层 auth_basic | ❌ **没有** | — | nginx 与本改造完全无关（见 §4） |
| 改 core 源码 | ❌ **没有** | — | 源码 checkout 的 `git status` 干净 |

### 3.4 账号密码存哪、怎么校验

**存储**：`$DSH_HOME/settings.yaml` 的 `auth-webserver` 命名空间。107 上实际内容（密码已脱敏）：

```yaml
auth-webserver:
  username: rooftop
  password: <secret-role 字段，明文存储但权限 0600>
  realm: DeepSeek Harness Authentication
  authEpoch: 1
```

**三层优先级**（`index.js:624-640` 与 `credentials()` at `:1042`）：

```
1. 环境变量  DSH_AUTH_USER / AUTH_USER 、 DSH_AUTH_PASS / AUTH_PASS   （最高）
2. settings 文档 $DSH_HOME/settings.yaml 的 auth-webserver 命名空间    （GUI 卡片写这里）
3. bundle 行配置 webserver-auth 的 config（cordis.patch.yml）          （基础层）
```

107 上**没有** `$DSH_HOME/.env`，也就是说**配置来自 settings.yaml（GUI 保存的），不是环境变量**。

**校验**：常量时间比较，不是普通 `===`：

```js
// index.js:150-154
function safeEqual(left, right) {
  const a = createHmac("sha256", "dsh-auth-compare").update(String(left)).digest();
  const b = createHmac("sha256", "dsh-auth-compare").update(String(right)).digest();
  return timingSafeEqual(a, b);
}
```

**口令为空则拒绝一切认证**（`index.js:1206`：`if (!pass) return null;`），但 core 的 loopback listener 照常工作。

**`authEpoch` 机制**：改动口令/2FA 时 `authEpoch` 递增，token 的 HMAC 输入里含 `authEpoch`，于是**所有旧会话立即失效**（`index.js:1066-1071` 启动时还会主动清理 epoch 不匹配的持久化记录）。

### 3.5 会话 token 与 CSRF 的构造

```js
// index.js:1072-1086  —— 生成
const generateToken = (req, user, pass, authEpoch, twoFactorEnabled, twoFactorSecret) => {
  const record = sessionStore.create({ username: user, address: clientAddress(req),
                                       userAgent: req.headers["user-agent"],
                                       secure: isSecureRequest(req), authEpoch });
  const sessionId = record.id;                       // randomBytes(16).toString("base64url”) → 22 字符
  const now = record.issuedAt;
  const signature = createHmac("sha256", secret)
    .update(`${sessionId}\u0000${user}\u0000${pass}\u0000${authEpoch}\u0000${tokenFactor(...)}\u0000${now}`)
    .digest("hex");
  return `${sessionId}.${now}.${signature}`;
};
```

- `secret` 是持久化在 `~/.dsh/plugins/dsh-plugin-auth-webserver/.secret` 的 32 字节 hex（`loadOrCreateSecret()`，`index.js:389`，权限 0600，会自愈权限）
- `tokenFactor` = TOTP 启用时 `mfa\0<secret>`，否则字面量 `"pwd"` —— **也就是说 token 的签名绑定了当前口令与 2FA 密钥**，改口令即全失效
- **CSRF**：`csrfForToken(token) = HMAC-SHA256(secret, "csrf\0"+token).base64url`，放在**非 HttpOnly** 的 `dsh_auth_csrf` cookie 里；每次写操作要 `X-DSH-CSRF` 头与 cookie **双向都等于** `auth.csrf`（`index.js:1247-1252`）
- **Cookie 命名随传输安全等级切换**（`index.js:1182-1196`）：
  - 明文 HTTP → `dsh_auth_token` / `dsh_auth_csrf`
  - 判定为 HTTPS（`req.socket.encrypted`，或**可信代理**发来的 `X-Forwarded-Proto: https`）→ `__Host-dsh_auth_token` / `__Host-dsh_auth_csrf` + `Secure`
  - 两种名字**互斥并互相清除**（登录时同时下发 4 条 Set-Cookie，其中 2 条是清空另一套）
- **服务端会话持久化**：`~/.dsh/plugins/dsh-plugin-auth-webserver/sessions.json`（0600，原子写，30s 节流）。**只存 sessionId / username / 时间戳 / address / UA / secure，绝不存 bearer 值**（`session-store.js` 第 47 行注释：`it stores no bearer token`）
- **双超时**：绝对寿命 24 小时（`sessionMaxAgeSeconds`，默认 86400），空闲 12 小时（`sessionIdleTimeoutSeconds`，默认 43200）

### 3.6 core-session-bridge：这套改造最精妙的一环

`core-session.js`（217 行）解决了一个真正的难题：**网关替远程用户持有 core 的 token/cookie，但不能把 core 的 bearer 泄漏给远端**。

```js
// core-session.js:122-167  —— 用 core 自己的东西换 core 的 cookie
async function bootstrapRequest(connection, target, timeoutMs, onRequest) {
  // 1) 从 DSH 的 client-connection 服务拿到"带进程启动 token 的 URL"
  const bootstrapUrl = new URL(connection.authenticatedUrl(target.origin));
  // 2) 严格校验这个 URL 只能是  http://<loopback>/ ?token=<唯一>  形态
  // 3) 自己发一次 GET，收 303 + 恰好一个 Set-Cookie
  // 4) 只接受名字匹配 /^dsh-auth-[A-Za-z0-9_-]+$/ 且带 Max-Age 的 cookie
}
```

配套的三个"剥离"函数（`core-session.js:58-105`）：

| 函数 | 作用 |
|---|---|
| `stripCoreCookies(header)` | 从**浏览器发来的** Cookie 头里删掉所有 `dsh-auth-*` |
| `attachCoreCookie(header, session)` | 换成网关独占的那一个 core cookie |
| `stripCoreSetCookies(headers)` | 从**上游响应**里删掉所有 `Set-Cookie: dsh-auth-*`，**绝不透传给远程浏览器** |
| `stripLaunchToken(rawUrl)` | 从转发路径里删掉 `?token=`（且能正确处理 `?a=1&token=x#hash` 这种拼接） |

**并发折叠**：`createCoreSessionBridge().ensure()` 用 `pending` promise 合并并发请求；cookie 距过期不足 5 秒（`COOKIE_REFRESH_SKEW_MS`）时自动重新兑换；上游返回 401 时 `invalidate()` 强制下次重兑（`index.js:1793`）。

**这就是"并行叠加"的物理实现**：core 的 token/cookie 层原封不动地保留着，只是**它现在只服务本机和网关**，远程用户看到的是网关自己的会话。

#### 摘录 1：Host / Origin 栅栏（防 DNS rebinding）

```js
// index.js:670-683
const validateGatewayRequest = (req) => {
  const host = req.headers.host;
  if (!hostMatches(host, allowedHosts, isSecureRequest(req))) {
    return { ok: false, status: 421, error: "Misdirected request" };
  }
  const origin = req.headers.origin;
  if (req.headers["sec-fetch-site"] === "cross-site" || !originMatches(origin, host, allowedOrigins)) {
    return { ok: false, status: 403, error: "Cross-origin request rejected" };
  }
  if (requireHttps && !isSecureRequest(req)) {
    return { ok: false, status: 400, error: "HTTPS is required" };
```

#### 摘录 2：认证核心（cookie 优先，Basic 兜底且受 2FA 禁用约束）

```js
// index.js:1204-1232
const authenticateRequest = (req) => {
  const { user, pass, twoFactorEnabled, twoFactorSecret, authEpoch } = credentials();
  if (!pass) return null;                                   // 未设口令 → 谁都不认

  const cookies = parseCookies(req);
  const names = cookieNames(isSecureRequest(req));
  const token = cookieValue(cookies, names, "token");
  if (token && verifyToken(token, user, pass, authEpoch, twoFactorEnabled, twoFactorSecret)) {
    const parts = token.split(".");
    if (sessionIsActive(parts[0], Number(parts[1]))) {
      return { kind: "cookie", token, sessionId: parts[0], issuedAt: Number(parts[1]),
               csrf: csrfForToken(token) };
    }
  }
  // Basic Auth cannot carry a second factor and is deliberately disabled when TOTP is active.
  if (twoFactorEnabled) return null;
  const basic = parseBasic(req.headers.authorization);
  if (!basic) return null;
  if (loginRateLimited(req, basic.user)) return null;
```

```yaml
# auth-webserver: pin the LAN gateway to the physical NIC only.
#
# The bundle default is `addresses: []`, which means "auto-detect every
# non-loopback NIC". On this host that includes docker0, cni0, flannel.1 and

    password: ''

    trustedProxyAddresses:
      - 192.168.105.67            # 反代真实源 IP（抓包确认）
    allowRemoteSettings: true
    allowInsecureRemoteSettings: true
```

同一份文件还记载了三个**上游缺陷/陷阱**（对移植极其重要）：

1. **`allowedHosts` 必须显式写**：0.7.6 里"既没 `allowedHosts` 也没 `allowedOrigins`"的分支返回的是 `pickAddresses()` 的**裸字符串**，而上面两个分支返回的是 `{hostname, port}` 解析对象。`hostMatches` 读 `allowed.hostname` 拿到 `undefined`，于是**每个请求都被 421 拒绝**，连登录页都出不来。
2. **定向到 `id` 的 `config:` 是整体替换而非合并**：只写 `addresses` 会让 `port`/`targetHost`/`targetPort`/`username`/`password` 全部消失。
3. **`trustedProxyAddresses` 的必要性**：只有在可信代理来源上，`X-Forwarded-Proto: https` 才被采信（进而下发 `__Host-` Secure cookie），`X-Forwarded-For` 才被采信（否则所有远程用户共享一个限流桶，一个人就能锁死全部人）。

## 五、与新版 token/cookie 模型的逐条比对

新版模型（Lead 实测 + 本次源码核对）：

| 概念 | 旧版 core（0.1.5-rc.2）原生 | 107 的 auth-webserver 插件 | 新版（0.2.0/0.2.1-rc.2）原生 | 关系 |
|---|---|---|---|---|
| 进程启动 token | `?token=` 一次性 | **原样复用**（`authenticatedUrl()`） | 同 | **等价**，插件只是"借用" |
| token→cookie 兑换 | 303 + `Set-Cookie: dsh-auth-*` | **原样复用**（`core-session.js`） | 同，但 `Location` 从 `/` 变为 `./` | **等价**（有细微差异，见 §6.2） |
| cookie 密钥 | `$DSH_HOME/.credentials.yaml` 的 `client-connection/browser-session` | 不参与 | 同 | **等价** |
| cookie 属性 | — | — | `HttpOnly; SameSite=Strict`，绑定 `authority`，30 天 | **等价** |
| Host/Origin 栅栏 | core 的 `/api` browser-trust fence | 网关**自己再做一遍**（`421`/`403`） | 同，`--trusted-host` 可扩 | **叠了两层**（网关一层 + core 一层） |
| API / WebSocket 鉴权 | ✅ | 网关先鉴权，再带 core cookie 打上游 | ✅ | **双层** |
| 多用户账号 | ❌ 无 | ✅ 账号密码 + `authEpoch` + client 列表 | ❌ 无 | **插件独有** |
| 登出 | ❌ 无 | ✅ `POST /api/auth.logout` + CSRF | ❌ 无（只能杀进程/换 cookie） | **插件独有** |
| 会话可撤销 | ❌ 无 | ✅ 按 client 逐条 revoke，立刻断 WS | ❌ 无 | **插件独有** |
| 第二因子 | ❌ 无 | ✅ TOTP + WebAuthn | ❌ 无 | **插件独有** |
| 限流 | ❌ 无 | ✅ 按 `clientAddress+username`，10 次 / 60 秒 | ❌ 无 | **插件独有** |
| 移动端/PWA | ❌ 无 | ✅ | ❌ 无 | **插件独有** |
| 绑 LAN IP | 需插件（core 只接受 `127.0.0.1`/`0.0.0.0`） | ✅ 逐 NIC 绑定 | 0.2.0 **不允许**；0.2.1 **允许具体 IP** | **已被上游吸收** |
| TLS | ❌ | ❌（靠外部反代） | 0.2.0 ❌；0.2.1 ✅（`--tls-cert`/`--tls-key`） | **已被上游吸收** |

**一句话**：插件的"传输层可达性"部分（绑 LAN、Host 栅栏）已被上游吸收；插件的"身份与会话治理"部分（账号、登出、撤销、2FA、限流）**上游至今没有**。

### 5.1 为什么它是「并行叠加」而非「替换」——三条硬证据

1. **源码层面**：`core-session.js:174-176` 要求 `typeof connection.authenticatedUrl === "function"`，否则**直接抛错拒绝启动**。它依赖 core 的 token 机制存在，不是绕过它。
2. **网络层面**：`127.0.0.1:3080` 的 core listener 在整个改造中**从未被关闭或改写**；同进程内两个 listener 并存（实测 `ss -lntp` 可见同 pid 两个 socket）。
3. **实现层面**：远程浏览器拿到的 cookie 是 `dsh_auth_token`（插件自造，HMAC 格式 `id.ts.sig`），而 core 的 cookie 是 `dsh-auth-<随机名>`（`v1.<base64 json>.<sig>`）。**两种 cookie 完全不同名、不同格式，各自工作在自己的 listener 上**。这一点在实际抓包中可直接区分（见 §6.3）。

## 六、可借鉴 / 不可借鉴（基于 `0.2.1-rc.2`）

### 6.1 可借鉴（且值得借鉴）

| # | 借鉴点 | 为什么仍然有价值 | 移植成本 |
|---|---|---|---|
| 1 | **"新模块而非替换"的架构** | 上游明确保留了 loopback listener，说明".core 仍然只信本机"是上游的设计约束；外挂网关是唯一不破坏该约束的做法 | 低 |
| 2 | **listener 分离判定"非本地"** | 比"查 `remote_addr` 白名单"稳健得多：不存在 IP 伪造、不存在网段误判、fail-closed（没监听 = 不可达） | 低 |
| 3 | **core-session-bridge 模式** | 新版 `authenticatedUrl()` 契约完全一致，这套"借 token → 换 cookie → 内存持有 → 剥离透传"的做法可直接照搬 | **低（契约未变）** |
| 4 | **账号密码 + `authEpoch` 全局失效** | 新版**完全没有**账号概念，多后端接入场景下这是刚需（每个后端一套凭据） | 中 |
| 5 | **显式登出 + 会话逐条撤销（含踢断 WS）** | 新版无 logout，只能关进程；桌面版接多后端时"切后端要清会话"必然遇到 | 中 |
| 6 | **CSRF 双校验（cookie + header 必须同时等于服务端派生值）** | 新版靠 `SameSite=Strict` + Origin 栅栏，是"防得住但不可登出"的取舍；需要表单/跨端时双校验更稳 | 低 |
| 7 | **`trustedProxyAddresses` + `X-Forwarded-Proto/For` 的可信来源白名单** | 桌面版若走反代/隧道，这条是"让 Secure cookie 与限流正确工作"的关键，且上游 `--trusted-host` 只解决 Host 不解决 forward 头 | 低 |
| 8 | **`421` + `Origin` 双栅栏的写法（`policy.js`）** | 110 行、零依赖、可直接复用；上游栅栏在 `/api` 层，网关需要在"进入 core 之前"就挡掉 | 低 |
| 9 | **会话存储只存元数据、绝不落 bearer** | 新版 `sessions.json` 若要加，这条是必须遵守的底线 | 低 |

### 6.2 不可借鉴 / 需要重写

| # | 不可借鉴点 | 原因 |
|---|---|---|
| 1 | **`settings.register()` 存取凭据** | `0.2.0-rc.2` 的 `@deepseek-ai/dsh-settings` 已**移除** `register()`，改成 `SettingsForms`（schema 直接来自插件 Config，命名空间 = profile entry id），`settings.yaml` 旧节会被 `importLegacyDocument()` 一次性迁移到 `.imported`。必须改用"插件 Config + `configure(presentation)`"或自管存储 |

| 3 | **`mobile.js` / `pwa.js` 注入** | 922+129 行针对 0.1.5 的 DOM 结构（rail 宽 56px、三栏布局、composer 工具栏 `flex-wrap`），新版 UI 大概率已变 |

### 6.3 一个直接的实测佐证（旧版 3080 现役行为）

```
$ curl -i http://192.168.55.107:3080/                 → 200  (登录页 "DeepSeek Harness - Sign in")
$ curl -i -u admin:wrong http://192.168.55.107:3080/  → 200  (仍是登录页；Basic 失败不弹 401 框)
$ curl -o /dev/null -w "%{http_code}" http://127.0.0.1:3080/  → 401  (core 的 token gate)
$ curl -H "Accept: application/json" http://192.168.55.107:3080/api/session.list → 401  (JSON 客户端拿到 401)
$ curl -H "Host: evil.example" http://192.168.55.107:3080/    → 421  (Host 栅栏)
```

**同一台机器上并存 401 与 200+登录页，正是"listener 分离"的最直观证明。**

### 6.4 一个必须说明的"选择"：为什么不直接依赖上游的新能力

即使 `0.2.1-rc.2` 已能绑 LAN + TLS，它仍然：
- 没有**身份**：任何人拿到 `?token=`（或已兑换的 cookie）就是 owner，无法区分"张三"和"李四"
- 没有**登出**：cookie 30 天有效，只能靠换 `$DSH_HOME/.credentials.yaml` 或关进程
- 没有**撤销粒度**：无法"踢掉某一台设备"
- 没有**审计**：无法知道谁在什么时候从哪个 IP 登录过

桌面版要"接多个 dsh 后端 + 鉴权"，这四条**恰好都是刚需**。所以结论是：**沿用 107 的架构思路（外挂网关 + 账号体系 + 借用 core token），但必须在新版 API 上重写，不能直接装 0.7.6。**

## 十、「升级后 yiln 那套鉴权网关还有用吗」——明确结论

**有用，而且在 `0.2.0-rc.2` 上是「必需」。**

### 10.1 论证链（全部为本次实测）

1. `0.2.0-rc.2` 的 `dsh-host-webserver` schema 只接受 `"127.0.0.1"` 和 `"0.0.0.0"`（`lib/index.js:142`）
2. `--host 192.168.55.107` → `ValidationError: $.host expected "127.0.0.1" | "0.0.0.0" but got "192.168.55.107"`
3. `--host 0.0.0.0` → `error: --host 0.0.0.0 is intentionally not supported yet for safety`
4. ⇒ **原生没有任何 LAN 可达路径**
5. ⇒ 唯一能监听 `192.168.55.107:3080` 的，就是网关插件自己起的 listener
6. 实测：不打补丁时 LAN `000`（不可达），打补丁后 LAN `200`（登录页）+ 登录 + GUI + WS 101

**所以升级不是"让网关变得可有可无"，而是把它从"锦上添花"变成"唯一通路"。**

### 10.2 三个版本的正确对照（避免误判）

| 版本 | 能否原生绑 LAN IP | 原生 TLS | 原生账号/登出/撤销/审计 | 网关的角色 |
|---|---|---|---|---|
| `0.1.5-rc.2`（升级前） | ❌ | ❌ | ❌ | 必需 |
| **`0.2.0-rc.2`（107 现在）** | ❌（只 `127.0.0.1`/`0.0.0.0`） | ❌（无 `--tls-*`） | ❌ | **必需，且是唯一路径** |
| `0.2.1-rc.2`（桌面内置） | ✅ 具体 IP | ✅ `--tls-cert/--tls-key` | ❌ | **从"唯一路径"降为"身份增强层"** |

对 `0.2.1-rc.2` 而言，网关不再通路必需——但它仍补上**新版至今没有的四件事**：多用户账号、显式登出、会话逐条撤销（含踢断 WS）、登录审计（client 列表 + IP + UA）。桌面版"接多个 dsh 后端 + 鉴权"的场景，这四件恰好都是刚需。

### 10.3 代价（必须一并接受）

| 代价 | 说明 | 缓解 |
|---|---|---|
| **必须打 2~3 处补丁** | `settings.register`（auth-webserver + web-daemon）+ `Location "./"` + 凭据搬进 row config | 补丁极小且已文档化；但不可长期依赖 `npm i` 重装（会被覆盖） |
| **失败模式是静默降级** | systemd `active`、token URL 照常打印，但 LAN listener 根本没起 | **必须**用 `ss -lntp \| grep <LAN_IP>:<port>` 做健康检查，不能只看 `systemctl is-active` |
| **`settings.yaml` 位置变了** | 新版会把它改成 `.imported`，可识别的节搬进 `cordis.patch.yml` | 凭据直接写 row config；其它配置从 `.imported` 手工搬 |
| **升级源受限** | 内网镜像缺 `node-addon-require-builtin@^0.1.9` | 安装时加 `--registry=https://registry.npmjs.org/` |
| **`web-daemon` 不可用** | 同类 `settings.register` 问题 | 不影响服务；需要时同样加 `typeof` 守卫 |

### 10.4 一句话结论

> 升级到 `0.2.0-rc.2` 之后，**yiln 的鉴权网关不但还有用，而且是这台机器唯一的远程访问方式**——因为新版原生把 LAN 监听彻底关死了（`127.0.0.1` 与 `0.0.0.0` 都不允许）。代价是必须打 3 处一行级补丁，且必须用「LAN listener 是否存在」而不是「systemd 是否 active」来做健康检查。对桌面版的 `0.2.1-rc.2` 而言，网关不再是通路必需，但它提供的账号/登出/撤销/审计仍是上游至今缺失的能力，因此**值得移植，但应按 0.2.1 的 API 重写，而不是直接装 0.7.6**。
